## 問題

候選組合多，需要限制求解量。

## 程式與合成對照

合成測試以相同候選與點距判準比較前兩名與全清單。只看短清單錯過可行弧。

```shell
dotnet src/Cli/bin/Release/net10.0/Cli.dll experiment run arc-ordering
```

輸出 `observations` 列出判定依據，`reproduced` 表示合成對照是否符合預期。 [實作](../../src/Core/Experiments.cs#L109)

## 設計假設與證偽

排序原先假設低成本前幾名可代表最有希望的幾何。有效條件是排序特徵與實際可行性有足夠關聯；這個條件必須用已知正例回放驗證，不能用搜尋沒找到來自證。

反例固定候選集合、幾何判準及正例，只改檢查順序／覆蓋範圍。短清單沒找到、完整清單找到，證明的是排程漏選，不是多弧不可行。後續分別記枚舉完整度、候選被剪原因、求解結果與預算耗盡；未定不記無解。

公開例只實作最小覆蓋反例，沒有重建公司全套多弧搜尋。新 [GeneralFitting](../../src/Core/GeneralFitting.cs)也明列候選嘗試與 budget flag，沒有宣稱全域最少。

歷史回放也發現可行模型落在早期排序之外。當時不能把搜索沒找到當成幾何無解。後續以正例回放與剪枝界分開記錄。

## 現行工程草稿中的角色

有限預算有助讓流程在可用時間內交出結果。漏選與未定要保存，不能將未找到稱成無解；工程候選可供審看，不能隱藏原搜索限制。 [現行交付判準](../engineering-acceptance.md)。
