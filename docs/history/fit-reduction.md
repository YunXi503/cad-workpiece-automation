# 保公差減段

**歷史狀態**　正式採用

## 問題

既有草圖元件太多，逐段編輯費時。

## 程式與合成對照

同一組合成線弧先保留切窗邊界，再合併相容段，原始與等分點都重新量距。

```shell
dotnet src/Cli/bin/Release/net10.0/Cli.dll experiment run fit-reduction
```

輸出 `observations` 列出判定依據。 [實作](../../src/Core/Experiments.cs#L260)

## 現在怎麼驗證這個決策

歷史正式採用的是「移除支持後重建，再核同一份全部點」的工程規則，並非任意合併鄰近圖元。現在的 [GeneralFitting](../../src/Core/GeneralFitting.cs)每次記原支持索引、前後段數、接受與否及拒絕原因，對有限曲線重算原點／等分點距離及 G1。

Case A 同一新引擎基準 227 → 165 段；歷史版 129 段雖較少，兩側超 0.3 mm。因此本版只說在固定公差下精簡，沒有用換公差、換草稿或只挑順利側來宣稱全面改善。詳[同一草稿比較](../original-case.md#線弧與取整實測)。

## 歷史另一件的實際減段紀錄

原專案另有Case B左側在既定0–305mm參考範圍、0.3mm公差不變下，由41→23段（12線11弧）。歷史紀錄列488候選：15通過、465拒絕、8未定；8未定沒有被記為無解。626原草稿點／626等分點最大XY為0.287322445283337mm，接點0，切向單位向量差6.02e-14，原首末支持與端點保持。

這是當時同版排程對照的結果，原始點／範圍／數值核保持，沒有證明23是全域最少。後來新版另建三草圖／三面，208有效約束，原生讀回2.07e-13mm以內；另兩側草稿仍超0.3，整件貼合未合格。這些是歷史Case B，不是本次原始Case A的165段收據，也不是本次新C#的一次實測。

歷史流程以支撐移除後重擬合，保留通過候選與未定項。公開版展示精簡與驗證契約，結果是在已試候選中取得。

## 現行工程草稿中的角色

減段應幫助編輯與加工，而非只追求段數最小。129／165 元件保留為不同工程取捨；更少元件或更小誤差都不能直接換算成節省工時。 [現行交付判準](../engineering-acceptance.md)。
